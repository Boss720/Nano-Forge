## 2. Logic Chain

1. **From Observation 1 & 4 (Zero NL Authority)**:
   - Because model output or chat text cannot satisfy approval gates, approval status must be tracked via an explicit `approvedStepIds: ReadonlySet<string>` ledger generated by user interaction in the UI.
   - Therefore, `readySteps` must accept an optional `approvedStepIds?: ReadonlySet<string>`. If a step has `approval: "required"`, it must be rejected unless `approvedStepIds?.has(step.id)` is explicitly `true`.
   - If `approvedStepIds` is undefined/omitted, steps requiring approval cannot run, ensuring security by default while maintaining backward compatibility for auto-approved steps.

2. **From Observation 1 & 2 (Topological Resolution & 7 Step States)**:
   - Phase 2 introduces 7 step statuses (`pending`, `ready`, `running`, `succeeded`, `failed`, `blocked`, `skipped`).
   - A step is ready to execute if its status is `"pending"` or `"ready"`, all its `dependsOn` steps exist in `plan.steps`, and each dependency has status `"succeeded"`.
   - Steps in active/terminal states (`running`, `succeeded`, `failed`, `blocked`, `skipped`) must be excluded from `readySteps`.

3. **From Observation 1 (Performance Optimization)**:
   - By creating a local `Map<string, PlanStep>` before filtering, `readySteps` resolves dependencies in $O(V + E)$ time rather than $O(V \cdot \text{deg} \cdot V) = O(V^2 \cdot K)$, preventing UI lag on complex DAGs.

4. **From Observation 3 (Test Suite Completeness)**:
   - A complete 22-test suite in `plan.test.ts` is required to verify:
     - Root & sequential execution
     - Diamond fork-join DAGs (all branches must succeed before join releases)
     - Approval gate enforcement, selective branch approvals, and revocation
     - Failure and skip cascades
     - Multi-phase cross-boundary dependencies
     - Dangling and cyclic dependency edge cases.

## 3. Caveats

2. **Backward Compatibility**: Calling `readySteps(plan)` without the second argument (`approvedStepIds`) continues to work for all legacy plans and auto-approved steps. Any step with `approval: "required"` will safely remain unreleased until explicit approvals are provided.
